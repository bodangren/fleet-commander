# Specification: Make Weight Tuning a Real Loop

## Overview

Dispatch scoring weights are static defaults in `pivot/src/policy/scoring.ts` (`DEFAULT_WEIGHTS`). There is no instrumentation to inform tuning, so each manual adjustment is a guess. This track closes the loop: capture per-dispatch score breakdowns, produce a weekly report, and make weight changes a safe config operation rather than a code change.

## Functional Requirements

### 1. Per-Dispatch Score Breakdown in Run Record

- On every dispatched task, persist the full `breakdown: Record<string, number>` from `scoreCandidate` alongside the task run record.
- Also record the eventual outcome for that task: accepted, rework, rejected, or regression.
- Audit what fields `scoreCandidate` currently emits and fill any gaps before persisting.

### 2. Weekly Tuning Report

- Implement a scheduled job that runs once per week.
- The job produces a markdown file at `measure/reports/scoring-weekly-YYYY-WW.md`.
- Report must include:
  - Per-factor contribution to winning scores over the week.
  - Correlation between each factor's value and task outcome.
  - Counterfactual: "if weight set X had been used instead of Y, what would have changed?"

### 3. Named Weight Presets

- Add `~/.measure-fleet/weight-presets.yaml` with named weight sets.
- Initial presets: "default", "cost-conservative", "speed-favored."
- Presets must be switchable per-fleet or per-project.
- Switching presets is a config-file change, not a code change.

### 4. Shadow Scoring (Optional)

- On each dispatch cycle, score candidates with both the active weights and one alternative preset.
- Record the alternative winner in the run log without acting on it.
- After two weeks of data, the weekly report includes a comparison of actual vs shadow selections.
- This item is optional and should be deferred if items 1–3 are not yet stable.

## Non-Functional Requirements

- Score breakdown persistence must not add more than 10ms to dispatch latency.
- Weekly report generation must run as a background job (non-blocking).
- Weight preset file must be human-editable YAML.
- Shadow scoring, if enabled, must not alter dispatch decisions.

## Acceptance Criteria

- [ ] `breakdown` and `outcome` persisted on every dispatched task run record.
- [ ] `measure/reports/scoring-weekly-YYYY-WW.md` generated by scheduled job.
- [ ] Report contains per-factor contribution, outcome correlation, and counterfactual.
- [ ] `~/.measure-fleet/weight-presets.yaml` exists with three named presets.
- [ ] Active preset switchable per-fleet or per-project without code changes.
- [ ] (Optional) Shadow scoring logs alternative winner without affecting dispatch.

## Out of Scope

- ML-based automatic weight optimization.
- Real-time scoring dashboard UI (Phase 6 planned).
- Storing presets in Convex (file-based only for now).
