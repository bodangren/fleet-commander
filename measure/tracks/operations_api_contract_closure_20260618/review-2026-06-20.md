## Code Quality Observations

- **Good:** Deleting `convex/pipelines.ts` instead of leaving placeholders is the correct architectural decision and matches spec criterion 7.
- **Good:** The `fnName()` helper in `pipelines.test.ts` using `Symbol.for('functionName')` correctly handles Convex FunctionReference identity instability — this is a reusable pattern worth documenting.
- **Concern:** `pivot/src/routes/pipelines.ts` uses `client: any` in `storeExecution` and `updateExecutionStatus`. This bypasses the typed boundary that the track's name ("typed convex boundary") implies should be protected. A follow-up should tighten these types.
- **Concern:** `storeExecution` maps the generic `execution` record to a `pipelineRuns.createPipelineRunHandler` call using `taskId: ((execution.triggeredByTaskId as string) ?? execution.id ?? 'unknown')`. The fallback to `'unknown'` could create invalid references; the track's adversarial tests catch some invalid-ID cases but the production route still permits it.
- **Concern:** `updateExecutionStatus` maps `cancelled` → `failed` because the target schema lacks `cancelled`. This is a semantic loss that should be documented or fixed in `pipelineRuns`.
- **Good:** `Reconcile.tsx` now surfaces both initial-load and action errors with `role="alert"` and `data-testid` attributes, satisfying accessibility and testability needs.

## Risks or Blockers

1. **Pre-existing `npm test` failures remain.** `pivot/src/routes/pipelines-args-validation.test.ts` has 3 adversarial test failures (invalid Convex IDs, response shape mismatch in mock env) that are documented as pre-existing and not owned by this track. They keep `npm test` at exit code 1.
2. **Typed boundary is loosened.** Using `client: any` in two pipeline helpers undermines the typed Convex boundary the track claims to close. Future refactors could re-introduce type errors silently.
3. **`convex/pipelines.ts` deletion orphan.** `pivot/src/routes/typed-convex-boundary.test.ts` was updated, but a global grep should confirm no other tests or docs still reference the deleted module.
4. **Reconciliation route error handling is coarse.** All failures return `{ error: 'internal_server' }` with HTTP 500; there is no differentiation between not-found and validation errors.

## Recommended Next Actions

1. **Restore typed client parameter** in `storeExecution` and `updateExecutionStatus` instead of `client: any`, or add a dedicated `ConvexClientLike` interface.
2. **Resolve or quarantine** the 3 pre-existing `pipelines-args-validation.test.ts` failures so `npm test` exits 0; if they require a real Convex runtime, document that dependency clearly.
3. **Add a route-inventory regression test** that explicitly enumerates frontend `/api/...` fetch URLs and asserts each is registered in `pivot/src/server.ts` or the route modules.
4. **Improve reconciliation error granularity** by returning 404 for missing proposals and 400/422 for validation failures, not blanket 500s.
5. **Run a global search** for `api.pipelines.` and `convex/pipelines` references in docs/tests to ensure no stale references remain.
